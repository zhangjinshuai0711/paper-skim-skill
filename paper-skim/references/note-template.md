# 阅读讨论整理成 Zotero 笔记

只有用户选了笔记选项或明确要求整理时，才使用本参考。结构来自用户认可的 INTEGER 阅读笔记；复用解释逻辑，不依赖原项目文件，也不照搬它的技术内容、数值或商品比方。

## 建议结构

按论文实际内容合并或省略不适用项，不要求机械凑齐标题。

1. **论文信息与一句话问题**：准确标题、方法名（如有）、固定版本/标识、笔记日期、实际阅读范围。
2. **Introduction：背景与问题的提出**：已有办法如何工作 → 具体障碍与需求 → 为什么不能简单处理 → 作者收束成什么研究问题。
3. **Methods：逐项解决机制**：先给输入到输出的完整流程，再按“要解决的困难 → 改了什么 → 怎样运行 → 为什么可能有用”解释关键设计。
4. **创新归纳**：对应研究困难与本文改变，分清沿用的骨干、已有技术和本文设计；不把“用了某技术”单独当作创新证明。
5. **必要证据与边界**：只留支撑核心机制的主结果或消融，写清参照配置、指标和数据/评分来源。实验未读时注明，不补表格。
6. **阅读结论与启发**：保留对本文的理解；如有改进想法，标成阅读者建议，不混成作者贡献。
7. **原文定位**：用可复核章节、表图和固定版本链接支持关键论断。

Methods 通常占最多篇幅；Introduction 与 Methods 是主体，其他部分用于支撑和限定它们。无需固定字数，也不自动堆全量超参数、术语表或公式推导。

## 整理时必须保留的区别

- 训练怎样学与使用时怎样运行；输入、关键中间量与输出。
- 模型、程序、工具或人的职责；训练标签和偏好对怎样定义好坏。
- 论文事实、辅助比方、个人解读与研究假设。比方可保留，但标明是辅助理解，避免把简化条件写成论文机制。
- 对照与消融的真实参照组、相对变化与百分点、作者报告与本轮复现。
- 本次用户追问后已经澄清或纠正的结论；不把前期误解带回最终笔记。

## 交付检查

- 论文名、方法名、版本和章节定位是否准确，是否有未替换提示文字或不可移植的会话引用标记？
- 笔记脱离聊天后，是否仍能看懂问题如何提出、方法如何解决，而不只知道模型有什么效果？
- 数值是否核算，Markdown 表格/代码/公式定界符是否成对，来源链接是否指向实际核对版本？
- 不把笔记自动套成用户的个人观点；用“阅读理解”“启发”并说明归纳性质。
- 保存后提供文件入口和核验范围；未直接写入 Zotero 时，不声称已经入库。
