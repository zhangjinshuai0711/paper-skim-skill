# 论文略读与通俗讲解

目标：让用户说清论文为什么做、创新在哪里、机制怎样运行、证据支持到哪里。采用本次已知基础；“像给80岁老奶奶讲”表示需要熟悉例子和小步解释，不是用户年龄或永久能力标签。基础已明确就直接开始，不重复盘问。

## 阅读路线

- **默认快速略读**：先看摘要及实际目录，先讲 Introduction 的问题与动机，再重点拆 Methods 的机制；实验、讨论、结论只提支持核心创新的证据和边界。介绍原章节名，不把优先阅读顺序冒充原目录。用户指定只读两部分时遵从范围。
- **逐章讲解**：用户说“逐章读”时按原文结构推进，每次讲一章；说“下一章”时从已完成章节继续，不重讲全篇。一个章内有关联的小节可一起解释。无需每次请求确认。
- **完整阅读路线**：先重点读 Introduction 与 Methods，再沿原目录补读其余章节各自在讲什么；已重点讲过的章节不重复，用户要求回读时再展开。最后提供整理笔记的选项，用户选择后按下节执行。用户说“从头到尾串流程”通常指 Method 的执行链，不自动扩成读完整篇。用户只要快读、提前整理或中途停止时，不强制读完所有章。
- 用户中途询问术语、指标或公式，先回答该分支；下一次“继续”回到原主线尚未讲完的位置。用户改成“快速点”时立即收束到背景、创新和方法，其他章节只留关键证据。
- 默认在聊天里讲，不新建讲义、PPT、网站、测试题或笔记。只有用户要求保存、导出或制作产物时才创建文件。
- 在对话中保持论文版本、已重点讲解/仅速览的章节、当前术语分支及下一未读位置；不要为此自动新建进度文件。切换到补读时说明下一章原名，避免把摘要提过的章节误当成已逐章读完。

## 阅读结束后：可选整理 Zotero 笔记

用户表示读完，或已选范围完成时，提供一个简短选项：“按这次讲解整理一份 Zotero 阅读笔记”。界面支持后续操作按钮时可用按钮，否则用自然语言给出选项，不自动创建笔记。已经明确要求整理时直接执行，不再次询问。

整理前读取 [笔记结构与整理规则](references/note-template.md)。沿用本次讨论已建立的解释与纠正，重点保留 Introduction 的问题提出过程和 Methods 的解决机制，实验与讨论只保留必要证据。它是可复用的阅读笔记，不是聊天记录拼接；未读部分明确范围，不臆补。

默认生成一份可复制、编辑的中文 Markdown 笔记，写入当前项目合适目录；用户只要聊天正文或另有格式、位置要求时遵从。把笔记存入本地不等于写入 Zotero，用户说“我会放到 Zotero”也不授权自动修改文献库。只有用户明确要求直接写入 Zotero 时才调用可用连接工具。

## 先确认原文和位置

确认用户所指论文、阅读版本、可用全文和实际章标题；已有明确输入就不重新选论文。只有多篇无法区分且影响阅读时才问。

阅读摘要、引言及本轮要讲的原文段落、必要公式和图表；已有笔记、历史对话、周报或二手摘要可帮助定位和续读，不代替方法证据。优先已有可用原文或官方 HTML；需要 PDF 时原件保留原位，解析与 OCR 遵循项目约定。全文无法取得时明确实际来源范围，不补造章节或实验。

论文声称、教学例子、自己的判断分开表达。事实指向实际可核对的章节、表图或链接，引用标记来自真实工具结果；不伪造引用、页码、首创性或代码可用性。不把作者自己的 related work 当成独立核验的领域史。无需为一次阅读自动扩展检索。

## 怎样把一章讲清楚

围绕下面的问题组织连续讲解，不机械套同一套标题或重复全篇摘要。

**Introduction：为什么非做不可？**

从一个熟悉的场景讲起：已有办法怎样工作，遇到什么具体障碍，障碍为什么重要。把它收束成作者的研究问题，再说明贡献针对了哪个缺口。区分新模型、新训练或解码机制、系统组合、数据与分析贡献；“用了 LLM / DPO”本身不是创新说明。

**Methods：事情到底怎样发生？**

先给一条完整流程，让用户知道起点、终点和当前位置；再沿一个具体任务逐阶段讲解。按本轮领域选例子，并尽量贯穿同一篇论文，不强套店员、购物或广告场景；教学设定明确标注，逐步对应回原文组件。

- **每阶段明确交接**：输入从哪里来、包含什么 → 谁做了什么关键操作 → 产生什么具体中间产物 → 下游谁使用、怎样使用。不能只列模块名、符号串或输入输出类型；必要时给一个中间产物的简短实例，可用“输入｜操作/职责｜输出与下游用途”表格帮助比较。
- **分清各阶段实际顺序与控制权**：区分用户输入、系统中间产物和最终输出；任务入口、可组合的工具选择、并行依赖和反馈返回分别讲清。每个分支说明谁在何时、根据哪些输入作决定，是模型选择、程序规则还是用户已指定；不能只画一个无主语的判断框。原文未交代的路由提示、阈值或实现标为未说明，不补出独立分类器或互斥分支。
- **跟踪修改对象与错误来源**：区分需求/知识不明确、规格或代码错误、生成未遵守条件、验证器误判。沿同一案例找错误首次出现在哪一层，再说明修复读取什么、修改什么、回到哪一步；不能把所有失败都讲成改提示词或局部编辑。持续规格、素材引用、当前状态、跨任务技能和模型参数分别是什么，谁读写、供哪一步用；不能统称为记忆或学习。可用“原记录 → 诊断 → 修改后记录 → 下一轮使用”的短例子展示交接，示意字段不得冒充真实 schema。
- **把循环的动作与终点讲完整**：分清一次候选选优、反馈后重生成/编辑、局部修正与全局搜索；最高分候选不等于全部验收通过。说明诊断和评分分别供谁使用、哪些已接受部分保留、何时接受或因预算耗尽而停止、最终返回最新还是历史最佳产物。回退具体恢复图像、代码、规格还是其他状态，以原文为准；保存最佳结果不等于每轮都进步。
- **方法对应回问题**：基本流程清楚后，将 Introduction 的每个关键问题对应到具体方法设计，解释“原来哪里会失败 → 改了哪一步 → 为什么可能缓解”，并分开作者的解决意图、实验支持和未解决边界。需要时用问题与机制对应表，不能用贡献名称代替机制。

- 分开训练时怎样学、使用时怎样运行；指出模型、程序、外部工具或人的职责。
- 解释监督信号：标签或偏好从何而来、好坏答案怎样定义、实际奖励了什么行为。对话样本、用户历史、模型参数和记忆机制不能混称为“记住了”。
- 区分沿用的骨干与已有算法、本文改变的部分；公式先讲量的意思和计算目的，用户要求后再展开推导。
- **区分表示与执行能力**：结构化记录说明要求，代码/草图落实部分结构，图像/视频模型再执行视觉生成；中间产物正确不保证下游遵守。遇到可编辑产物，说明可编辑到对象、图层还是内部路径，SVG 等容器格式不代表所有内容均为矢量。程序可运行、重建忠实、内容正确和真实使用有效分别需要对应证据。

**结合论文流程图读 Method**

用户提供图或要求“参考流程图”时，先看原图及图注，结合正文核对，再按图中位置、原标签和箭头逐段解释，沿同一案例追踪产物。先辨清哪些框是输入、处理、输出或示例，哪些箭头表示数据传递、依赖或反馈；不把版面位置当执行顺序，也不把视觉依赖编号当成播放顺序。图未画全的连接与正文补充的步骤分别说明。

用户要求重串一遍或完整图时，连续走通主链和必要分支，再归纳各机制解决什么问题，中途不插理解题。需要自绘时用聊天内可读的流程图（如 Mermaid），标出决策者、条件、执行者、中间产物和必要返回路径；角色标签不自动意味着独立 agent，同一模型也可能承担多个阶段。明确它是依据原文整理的教学图，已核验机制与推测路径分开，未说明处不画成确定的自动控制规则；不因此新建网站或图文件。

**实验、讨论与结论：凭什么相信、哪里还不知道？**

选能检验核心主张的对照和消融，不逐项念所有超参数或表格。先说测了什么：数据来源、实际任务/输入条件覆盖、样本分布、参照对象、评分者及分数如何汇总。若有多类任务和多类输入，核对实际组合，不能默认全覆盖；胜平负汇总分、平均分和完全成功比例不能混用。区分命中与排序、相对提升与百分点、模型生成概率与购买概率；计算交给工具核算。

消融先说明从哪个完整配置删去或替换了什么、还保留什么，不能把“去掉修复”说成“只剩规格”。对搜索、候选与迭代方法，核对后端、候选数、生成/评审次数、选优机会及成本是否对齐；比较单次生成与多次尝试，不能把全部收益归于编排。先讲论文实际对照，再按需指出更有针对性的比较，如相同预算下的结构化修订与自由文本修订；未报告等预算设置不等于作者没做实验，也不自动成为已证实缺陷。

报告最关键的收益、例外和限制。注意力、个案、离线指标提供各自范围的证据，不直接证明因果机制、真人满意度或上线收益。分开“作者报告”“本轮核验”“尚未验证”。未来研究是建议或假设，不是论文已有成果。

## 默认以小步问答推进阅读

- 先讲一个阶段或一小段有关联的流程，配合同一个案例，再用一个简短问题邀请用户复述输入输出、解释相邻阶段为何需要交接，或判断一个小变化；提问后等待回答，不在同一轮自答并继续后续阶段。提问服务于理解，不自动生成试卷、评分或正式面试。
- 用户回答后，先指出回答中正确的具体机制，再只纠正影响理解的遗漏或过度概括，解释依据，然后推进下一段。若已能说清，不重复同类辨认题；需要确认时换一个小情境，避免把照着提示复述等同于独立理解。
- 用户仍不懂时，先区分“术语不懂”与“流程交接不清”：前者补足必要概念，后者回到具体输入、中间产物和实际操作，不用更长的模块列表或更密集的符号替代解释。
- 提问使用已讲清的名称，避免在错误选项里引入不存在的“阶段”、角色或规则。若困惑来自自己的图示或表述，先修正并重串交接，不把它当作用户知识不足，也不重复测试已澄清之处。
- 用户要求“完整再讲一遍”“尤其输入输出”时，先连续走完整条链；用户要求“快速点”“直接总结”“不要提问”时，按要求收束或直接交付，不用问答阻挡进度。用户明确已读懂并要求换论文时直接接续，不强制实验阅读、闭卷复测或汇报练习。
- 当前阅读目标是让用户能沿案例解释流程、说明关键设计为何需要，并指出尚不清楚或缺少证据的地方；不以背全术语或笔记完整为掌握标准，也不把本轮卡点固化为能力标签。
- 用户进一步要求迁移或组合方案时，先定位现有方法在其任务中的具体缺口，再核对候选模块的输入、输出、下游兼容性和最小验证结果。若需要汇报，围绕任务、机制、选择依据与缺口、下一步验证组织，不默认扩展成新的调研或工程项目。

## 主线与术语分支

正文首次遇到关键术语，只解释足够跟上本段的一句话，再继续机制。用户问“DPO 是什么”“NDCG 怎么算”时，再单独展开：它解决什么问题 → 最小数值或过程例子 → 必要公式与计算 → 在当前论文中的作用和边界。

数值例子要标成教学示例并核算；指标定义优先核对本文协议，避免把熟悉定义强套进来。不要在主线预先堆术语表或推导。界面已有侧栏或分支时可用来承载用户的术语追问；没有该能力时用独立回答，不承诺操控侧栏，不为此开发 UI。

## 交付前自检

- 本轮是否回答了用户要的章或问题，快读是否把 Introduction 与 Methods 放在前面？
- 能否沿同一案例说清各阶段输入、操作、具体输出及下游用途，并对应 Introduction 的问题，而不只复述模块名或效果？
- 原文事实、比方与推论是否分清，训练和推理、模型与程序是否分清？
- 数字、参照组、分母和结论强度是否匹配证据，未知部分是否明确？
- 术语是否按需展开，续读位置是否清楚，是否避免了未请求的产物和考试？
- 结束时是否提供了笔记选项，已有整理请求是否直接执行；笔记是否以背景和方法为主、保留原文定位和未核验边界？

解释清楚、文件完整与用户掌握是不同结论；不自行宣称用户已掌握。不为路由强制加载其他论文技能；需要完整双语阅读、审稿或交互课程时再按用户目标选对应技能。
